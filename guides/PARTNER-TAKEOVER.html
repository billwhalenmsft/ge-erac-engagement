GE Verisk ERAC — Lite CRM · Partner Takeover Guide

Audience: a systems integrator or delivery partner (e.g. PwC) taking the ERAC Lite CRM turnkey — to operate, extend, or fold into a broader D365 program. Companion docs: BUSINESS-TRANSITION-GUIDE.md (business context) and TECHNICAL-HANDOFF.md (install + schema).

1. Purpose of this guide

You are receiving a complete, self-contained Power Platform solution plus its build harness. The intent is a turnkey takeover: you can stand this up in the customer's environment, own it, and extend it — without needing the original author, the original demo tenant, or any hidden dependency. This guide tells you exactly what you're getting, how to reproduce it, and where the extension seams are.

This mirrors how other Microsoft turnkey accelerators are handed to partners (the same genericize-and-build discipline used for the SAP Procurement and Ascend accelerators).

2. What "turnkey" means here (the guarantees)

Guarantee How it's assured
Installs in the customer's own tenant All source-env identifiers (org host, environment GUID, solution GUID, author) are genericized out; regenerated on import
No hidden dependencies Core CRM has no premium connectors, no cloud flows, no external service required
Reproducible from source An idempotent, phase-based provisioning harness rebuilds the environment from scratch
Verified before release An automated leak-check fails the build if any identifying token survives genericization
Solution-based naming The erac_ prefix describes the solution (Enterprise Risk & Advisory Consulting), not a person — safe to keep

3. The architecture you're taking over

┌─────────────────────────────┐
│  ERAC Lite CRM (MDA)        │  ← Users work here (native D365 chrome)
│  sitemap: Cedents · Engage  │
│  · Risk · Actuarial · Legal │
│  · Analytics                │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│  Dataverse                  │  ← System of record (all data)
│  • account/contact/task/    │
│    appointment + erac_* cols│
│  • 5 custom erac_ tables    │
│  • filtered views (cedent)  │
└──────────────┬──────────────┘
               │ (optional)
               ▼
┌─────────────────────────────┐
│  Copilot / Azure Function   │  ← OPTIONAL engagement-AI sidebar
│  (reads live Dataverse)     │     — not required for core CRM
└─────────────────────────────┘

No Power Automate layer. Unlike flow-based accelerators, ERAC's optional intelligence is a Copilot/Function sidebar, so there are no unpackaged connection references to remediate on import — the single most common cause of failed accelerator installs simply does not apply here.

Schema at a glance

  • Extended standard tables: account, contact, task, appointment (with erac_* columns: cedent flag, tier, partnership/PRR rating, function, Kanban stage, engagement fields).
  • Custom tables: erac_partnershiprating, erac_riskassessment, erac_treaty, erac_reserveadequacy, erac_dispute.
  • Cedent scoping: everything filters on erac_iscedent eq true.
  • Full definitions: customers/ge_erac/dataverse/config/schema.json.

4. Two ways to deploy (pick per engagement)

4a. Managed solution import (recommended for the customer's environment)

Import ERACLiteCRM_managed.zip via make.powerapps.com → Solutions → Import. This is the supported, upgrade-friendly path. See TECHNICAL-HANDOFF.md §3.

4b. Scripted reproduction (recommended for your dev/test + extension work)

Rebuild the whole environment from the idempotent provisioner:

cd customers/ge_erac/dataverse/scripts
.\Provision-EracDataverse.ps1 -OrgUrl "https://YOUR-ORG.crm.dynamics.com"           # full
.\Provision-EracDataverse.ps1 -OrgUrl "https://YOUR-ORG.crm.dynamics.com" -Phase Schema
.\Provision-EracDataverse.ps1 -OrgUrl "https://YOUR-ORG.crm.dynamics.com" -WhatIf   # dry run

Use 4a to deliver to the customer; use 4b to reproduce, diff, and extend safely.

5. Rebuilding / re-genericizing the package yourself

If you extend the solution and need to re-cut a clean, genericized package, the build harness is included:

# 1. Export + unpack the solution from your build environment
pac solution export --path ./out --name ERACLiteCRM --managed false
pac solution export --path ./out --name ERACLiteCRM --managed true
pac solution unpack --zipfile ./out/ERACLiteCRM.zip --folder ./solution_src

# 2. Genericize → validate → leak-check → pack (fails if any identity survives)
python customers/ge_erac/dataverse/solution/genericize_and_build.py

The harness runs three disciplines in order — genericize (scrub the identifier map), validate (OPC namespaces / ImportExportXml / inline entities — the ZIP-killers), and leak-check (build fails if a source identifier survives) — then packs the shippable ZIP. This is the same pattern used across Microsoft's turnkey accelerators.

6. Prove the install (the reliability gate)

Before you hand the package to the customer as final, prove it installs cleanly:

  1. Import into a fresh trial org (not your build env) via §4a.
  2. Verify against TECHNICAL-HANDOFF.md §8 (app opens, views return rows, all 5 tables present, no source identifiers).
  3. Repeat on a second fresh org — reliable means repeatable, not a one-off.

Only after a clean import on an environment that never saw the source is the package "proven."

7. Extension seams (where to build Phase 2)

Phase 2 workstream Seam Notes
Actuarial workspace erac_reserveadequacy table + Analytics area Reserving analytics, experience studies
Legal workspace erac_treaty + erac_dispute tables + Legal area Treaty tracking, arbitration dashboard
Contract/treaty integration Read-only views over an external contract system Surface treaty/contract data in CRM
Copilot Studio agent Dataverse built-in connector NL assistant over live cedent data — no custom API
Legacy migration Dataverse import / dataflows Bring historical CRM data forward
ERP convergence Dataverse ↔ D365 ERP See §8 — the PwC ERP evaluation

Build Phase 2 in a layered solution on top of ERAC, not by editing the base — this keeps upgrades clean.

8. The ERP context (why this matters to a PwC-led program)

ERAC is being evaluated alongside a Dynamics 365 ERP decision in which the partner is engaged. The Lite CRM is deliberately the relationship / front-office system of record; the ERP program is the back-office transformation. The convergence points a partner should plan for:

  • Shared party/account master — cedent accounts in CRM ↔ business partners in ERP.
  • Dataverse as the common fabric — both sit on Power Platform, so integration is native, not point-to-point.
  • One security & identity model — the customer's Entra tenant governs both.

Taking the CRM turnkey now gives the program a live front-office proof point while the ERP evaluation proceeds — and a clean base to converge into.
